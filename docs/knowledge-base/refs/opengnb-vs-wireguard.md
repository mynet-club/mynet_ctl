# OpenGNB 与 WireGuard：协议与架构对比

> 前置阅读：[`opengnb.md`](./opengnb.md)、[`wireguard.md`](./wireguard.md)。
> 本文只做原理层面的对比，不涉及任何具体项目的落地方式。

## 0. 一句话结论

**这两者不是同一类东西，把它们放在一起比较「谁更好」是范畴错误。**

- **WireGuard 是一个密码学协议 + 一个内核隧道接口**。它解决「两个已知公钥的端点
  如何安全地传 IP 包」。它**刻意不解决**密钥分发、地址分配、NAT 穿透、
  谁该和谁通信。
- **OpenGNB 是一个去中心化的组网系统**。它解决「一群彼此不知道对方地址的节点
  如何互相发现、穿透 NAT、建立虚拟网络，并在穿透失败时仍能通信」。
  它把身份、发现、穿透、转发**四件事打包在一起**。

所以正确的读法是：**WireGuard 是「隧道」，GNB 是「组网」**。
一个 GNB 网络里可以没有 WireGuard，一个 WireGuard 网络里可以没有 GNB；
而把 GNB 当作 WireGuard 的 NAT 穿透层、或把 WireGuard 当作 GNB 的数据面加固层，
都是成立的组合方式。

## 1. 设计目标的分野

| | OpenGNB | WireGuard |
|---|---|---|
| 官方自我定位 | 去中心化的软件定义虚拟网络（SDVN），「极致的 NAT 穿透能力」 | 「极简而现代」的 VPN 隧道，目标是比 IPsec 更简单、比 OpenVPN 更快 |
| 拓扑假设 | **节点对等**，没有 Server / Client 概念 | **点对点**，双方各自持有对方公钥 |
| 核心难题 | 地址未知 + NAT 阻隔 + 无中心 | 密码学正确性 + 实现可审计 |
| 对「中心」的态度 | 允许 index 节点做地址索引（类似 DNS / tracker），但**不依赖它中转数据** | **没有中心概念**；`AllowedIPs` 决定一切 |
| 明确排除的范围 | （未明确排除，但默认不转发全流量、不支持 CIDR） | **密钥分发、配置推送、混淆** 全部明确排除 |
| 代码定位 | 用户态 C，无第三方依赖，可跑到 32 MB 内存的路由器上 | **Linux 内核内**实现，追求「单个人可完整审计」 |

### 1.1 一个关键的分歧：状态与「连接」的概念

WireGuard 的规范用整节解释它为什么是「**无连接**」（Connection-less）的：
握手每几分钟发生一次，**基于时间而非基于此前数据包内容**触发，
理由是「**为了优雅地容忍丢包**」。官方原话是「你把设备启起来，
剩下的一切自动完成——不需要请求重连、断开或重新初始化」。

GNB 则相反：它有**显式的连接状态机**。
每个节点维护 `udp_addr_status` 位掩码
（`UNREACHABL` / `IPV4_PING` / `IPV6_PING` / `IPV4_PONG` / `IPV6_PONG`），
PING 间隔 37 秒、75 秒超时、连续 32 次探测失败判定失联。
「是否已建立 P2P」是**一等状态**，直接决定走哪条转发路径（§4）。

这不是设计品味差异，而是**问题性质差异**：
WireGuard 的「对端在哪」由配置给出（endpoint 或漫游发现）；
GNB 的「对端在哪」本身就是它要解决的问题，所以必须显式建模。

## 2. 身份与密钥体系

| | OpenGNB | WireGuard |
|---|---|---|
| 节点标识 | `nodeid` / `uuid64`，**64 位整数**（路由与配置索引） | 无独立 ID，**公钥本身即身份** |
| 密码学身份 | ed25519 密钥对（32 字节公钥 / 64 字节私钥文件） | Curve25519 密钥对（32 字节） |
| 私钥存储布局 | **`SHA512(seed)` 64 字节**，非标准 `seed‖SHA512(seed)`；**无法从私钥反推 seed** | 32 字节原始私钥 |
| 共享口令 | `passcode`（4 字节 / 32 位十六进制），混入密钥派生 | **PSK**（32 字节，可选），未启用时视为全零 |
| 索引层标识 | `key512 = SHA512(public_key ‖ passcode)` | 无（无索引层） |
| 密钥分发 | 靠 index 交换公钥 + `address.conf`；**lite 模式完全不加密** | **明确不在范围内**，靠带外交换（如 SSH 公钥） |
| 节点角色 | 位掩码：`IDX` / `FWD` / `RELAY` / `SLIENCE` / `STATIC_ADDR` | 无角色概念，所有 peer 平等 |

### 2.1 两者的「密钥派生」思路完全不同

**WireGuard**：从一次性的握手状态里派生会话密钥，握手的 chaining key
经过 4 次 DH 与 PSK 混合，最终得到 `sending_key` / `receiving_key`，
然后**把所有握手状态清零**。

**OpenGNB**：没有「会话」概念。每个对端节点有长期存在的 `shared_secret`，
它是**两个静态 ed25519 密钥对之间的 DH 结果**，然后

```
crypto_key = SHA512( [time_seed | shared_secret] ‖ shared_secret ‖ passcode )
```

这个 `crypto_key` 长期有效（除非开启时钟轮换），并且**同时用于数据面加密
和 index 帧的加密**。

**这个差别决定了前向保密的有无**，是两套系统在安全模型上最本质的分水岭（§3.3）。

## 3. 数据面安全模型对比

### 3.1 对照表

| 维度 | OpenGNB 1.6.8 | WireGuard |
|---|---|---|
| 对称加密 | **XOR（默认）或 RC4**；`--crypto` 取 `xor`/`rc4`/`none`，手册注明「未来会支持 aes」 | **ChaCha20-Poly1305**（RFC7539 AEAD），无协商、无降级空间 |
| 密钥流性质 | XOR 模式是 **64 字节固定周期重复密钥**，**无 nonce / IV** | 标准流密码，nonce = 32 位零 ‖ 64 位小端 counter，**永不重用** |
| 完整性保护 | **无 MAC / HMAC / AEAD**。`verifycode`（4 字节 = 明文首 2 + 末 2 字节）**不依赖密钥，可被攻击者重算**，只用于判断用新旧哪把密钥解密 | **16 字节 Poly1305 认证标签**；篡改必被发现 |
| 前向保密 | **无**。密钥由静态密钥对派生；时钟轮换只削弱问题，且引入时钟同步依赖 | **有**（数据包层面）。临时密钥 + 派生后清零；120s 重协商、180s 强制丢弃 |
| 抗重放 | 未见数据面重放窗口机制 | 64 位计数器**不可回绕** + **8128 位滑动窗口**，且**先验认证标签再查窗口** |
| 抗 DoS | index 侧限频（提交 20s / 查询 20ms）；forward 协议强制验签 | mac1/mac2 + **无状态 cookie**（对发送者 IP 的 MAC，密钥 120s 轮换，即 IP 所有权证明） |
| 身份认证 | ed25519 签名（**标准 RFC8032**，任何标准库可验证） | 握手内嵌认证（Noise_IK），无需额外签名层 |
| 握手次数 | 无握手；控制帧按需签名/验签 | **4 次 DH**，2 条消息完成 |
| 单跳封装开销 | **28 字节**（4 字节 payload16 + 24 字节 route_frame_head） | **32 字节**（16 字节头 + 16 字节认证标签）+ 填充至 16 倍数 |
| 默认 MTU | 1280（IPv6 下限）；IPv4 恶劣网络可降至 532 | 通常 1420（1500 − 40 IPv6 − 8 UDP − 32 WG） |

### 3.2 关于 GNB「非对称加密」说法的准确理解

GNB 的 README 写「GNB 主机之间的**非对称数据加密**使得 forward 节点无法窥探中转的数据」
（`src/README_CN.md:262`）。这个措辞容易被误读，需要拆开：

- **数据面用的始终是对称密码**（XOR / RC4）；
- forward / relay 节点无法解密，**原因是它们不在 DH 的双方之内**，
  而不是因为数据面用了非对称加密；
- 非对称部分（ed25519）负责的是**身份认证与密钥协商**，不是数据加密。

换句话说，GNB 的安全性建立在「**DH 共享密钥的保密性**」这一个支点上，
而 DH 结果又被用来当 XOR 的密钥流。一旦这个支点被攻破
（例如节点私钥泄露 → 可重算 `shared_secret` → 可重算 `crypto_key`），
数据面就没有第二道防线。

WireGuard 则有明确的分层：即使静态私钥泄露，
**已建立的会话密钥仍然安全**（前向保密），历史流量也无法被解密。

### 3.3 前向保密：为什么这个差别最重要

| 场景 | OpenGNB | WireGuard |
|---|---|---|
| 节点私钥泄露，攻击者有历史抓包 | 可重算 `shared_secret` 与 `crypto_key`，**配合 XOR 密钥流的结构性弱点，历史流量可被解密** | 会话密钥已随握手状态清零，**历史流量仍不可解密** |
| 节点私钥泄露，攻击者想冒充 | 可伪造签名，**可以冒充** | 可冒充，但**无法解密既有会话** |
| 密钥轮换 | 默认关闭；开启后依赖两端时钟同步 | 时间驱动，自动，无需配置 |

这就是为什么**「GNB 承载敏感数据时需要叠加一层加密」**是个合理的工程结论——
不是对 GNB 的贬低，而是两套系统设计目标的自然结果：
GNB 优先穿透与轻量，WireGuard 优先密码学强度。

### 3.4 一个反直觉但重要的点：GNB 的 XOR 弱点

XOR 模式的具体实现是（`packet_filter/gnb_pf_crypto_xor.c:52-59`）：

```c
for (i = 0; i < ip_frame_size; i++) {
    *p = *p ^ dst_node->crypto_key[j];
    p++; j++;
    if (j >= 64) j = 0;         // 64 字节后回绕
}
```

密钥流**就是** `crypto_key` 这 64 字节本身，周期固定 64 字节，没有 nonce。
这带来两个可被利用的性质：

1. **同一明文位置在任何包中产生相同密文**——可以跨包比对；
2. **64 字节周期使「已知明文结构」的利用成为可能**——
   IP 头与 TCP 头高度规整（版本号、IHL、TTL、端口等位置可预测），
   若攻击者能猜到 64 字节周期内的部分明文，就能恢复密钥流的相应字节。

所以 GNB 的 `--crypto` 默认值 `xor` **不应该被视为「加密」**，
它更接近「编码」。要提升强度至少应选 `rc4`，且两者都不解决完整性问题。

## 4. 地址发现与 NAT 穿透

这是 GNB 独有、WireGuard 完全不做的一层。

| | OpenGNB | WireGuard |
|---|---|---|
| 地址发现 | **有**。index 节点类似 DNS + BitTorrent tracker，节点提交自身 WAN 地址、查询对端地址 | **无**。端点来自配置（`Endpoint=`）或漫游自动更新 |
| 索引协议 | 5 类帧：`POST_ADDR` / `ECHO_ADDR` / `REQUEST_ADDR` / `PUSH_ADDR` / `DETECT_ADDR` | 无 |
| 索引侧状态 | LRU 表，每节点保留最近 3 个 IPv4 + 3 个 IPv6 地址 + WAN 地址 | 无 |
| 抗伪造 | `safe_index` 开关：**secure 版对所有 index 帧签名+加密；普通版完全不验签** | 不适用 |
| NAT 穿透 | **有，且是核心能力**。不判定 NAT 类型，靠「尽一切办法多试」 | **无**。WireGuard 假定至少一端可直达，或已有可达 endpoint |
| 穿透手段 | 多 index、`multi-socket`（额外 4 个随机端口）、端口探测、UPnP、地址扩散、Discover In Lan | 无 |
| 打洞促成方式 | index 收到查询后**同时向双方**推 `PUSH_ADDR_ACTION_CONNECT`，两端同时发包以在各自 NAT 上开洞 | 不适用 |
| 内网发现 | `gnb_es --discover-in-lan`：UDP 广播发现同 LAN 节点，直接以 LAN 地址建 P2P，**不必绕 WAN** | 无 |
| 穿透失败兜底 | 四种转发模型（§5）保证仍能通信 | 无兜底——不可达就是不可达 |

### 4.1 「不判定 NAT 类型」是刻意的

GNB 手册里有一段相当直白的表态（`gnb_user_manual_cn.md:568-572`）：

> **Don't talk about the white paper, who known? who care?**
> **Don't talk about the type of NAT, I don't f\*cking care**
> **What GNB has to do, just try it's best to traverse the NAT**

所以 `gnb_address.c` 里**没有** symmetric / cone 之类的枚举，
只有掩码分类函数。策略是穷举：多个 index、多个监听端口、
多个出口地址、大范围端口探测，加上「已穿透节点帮未穿透节点转发」的网络效应。

官方甚至指出这个网络效应：**虚拟网络中节点越多，节点之间越容易穿透成功**
（`gnb_user_manual_cn.md:391`）——因为可用的中转节点变多了。

### 4.2 WireGuard 的 roaming 是「反向的发现」

WireGuard 不做发现，但它有一个相关的机制：**端点随包自动更新**。
双方都把加密数据发往「最近一次成功认证解密」的 IP endpoint，
因此两端都有完整 IP 漫游，**不需要额外往返或认证**。

但官方把它列为已知局限（"Roaming Mischief"）：
**没有额外认证意味着主动中间人可以替换源 IP**，
甚至可能在失去中间人位置后仍能中继包。
机密性不受影响（包仍不可解读），但**可达性可能被影响**。
缓解手段是把 WireGuard 的 socket 用防火墙锁定到特定 IP。

GNB 的对应机制是 `SLIENCE` 角色（不与 index 通信、不响应探测，避免暴露 IP）
和 `--address-secure`（日志中隐藏部分 IP）——但 GNB 是**地址必须暴露给 index
才能被穿透**，所以两者的「隐私」取舍方向正好相反。

## 5. 转发与路由模型

| | OpenGNB | WireGuard |
|---|---|---|
| 转发模型 | **四种**：Direct（P2P 直发）/ Standard（经公网 forward 节点）/ Relay（自定义中继路径，逐跳再加密）/ Unified（借道已穿透节点，可多路径重传） | **一种**：`AllowedIPs` 决定的直发。没有中继概念 |
| 决策优先级 | `relay > unified > direct > standard` | 无（`AllowedIPs` 唯一决定） |
| 路由表语义 | `route.conf` 是**放行白名单**，不是路由表。实际路由由**系统路由表**决定 | `AllowedIPs` **双向生效**：发送时像路由表，接收时像 ACL |
| 子网支持 | **只支持 /32、/24、/16、/8、/0**。非标准掩码（/27、/22…）**被静默忽略，不报错** | **完整 CIDR**，任意前缀长度 |
| 多节点/多路径 | 支持。同一子网可挂多个节点（节点环，最多 128），容错或轮询负载均衡；Unified 可多路径重传做「TCP 加速」 | 不支持。一个目的地址只对应一个 peer |
| 环路处理 | 逐跳转发靠 TTL（=5）与 relay 数组 | 官方承认**路由环路检测存在问题** |
| 转发加密 | relay 路径**每一跳用下一跳的密钥重新加密** | 无中继，故无此问题 |

### 5.1 两个「路由」概念的关键差异

**WireGuard 的 `AllowedIPs` 是双向的**，这是 Cryptokey Routing 的精髓：

- **发送**：包的目的 IP 匹配哪个 peer 的 `AllowedIPs` → 用那个 peer 的公钥加密。
  都不匹配 → **丢包**。
- **接收**：解密后，明文的**源 IP** 是否在该 peer 的 `AllowedIPs` 里 → 决定是否接受。

所以管理员不需要 IPsec 那种复杂防火墙扩展，只需匹配
「是不是来自这个 IP？在这个接口上？」就能确信包可信。

**GNB 的 `route.conf` 是单向的白名单**：只决定「这个目的 IP 允不允许走 GNB、
走哪个节点」。发送与接收各检查一次（TUN→INET 与 INET→TUN），
但**它不表达「对端被允许使用什么源地址」**——
GNB 的接收检查验证的是**目的 IP** 是否在白名单里（准备写入 TUN 之前），
而不是源 IP 的身份绑定。

### 5.2 CIDR 支持的差异有实际后果

WireGuard 支持任意 CIDR，所以 `AllowedIPs = 10.0.0.0/12` 这类配置是自然的。

GNB **只认三种掩码**（`255.0.0.0` / `255.255.0.0` / `255.255.255.0`），
其余返回 `'n'` 并**静默忽略**。这意味着：

- 想覆盖 `192.168.0.0/16` 必须写成 B 类 `192.168.0.0|255.255.0.0`；
- 想覆盖 `10.20.0.0/22` 这样的非标准块**无法直接配置**，
  只能配更宽的 `10.0.0.0|255.0.0.0`（副作用是放行了整个 10/8），
  或者退化成逐条 C 类（每个 C 类占一个哈希表条目）；
- **精细粒度必须交给系统路由表**——这也是 GNB 官方文档推荐的组合用法：
  「GNB 只配节点和大网段，系统路由实现精细控制」。

这个限制在容量上也有体现：各类子网映射表容量为 1024 条。

### 5.3 Unified Forwarding 的代价

GNB 的 Unified Forwarding 在 `super` / `hyper` 模式下会
**对同一 IP 分组通过多个中转节点同时重传**，先到的被写入网卡，
重复的靠 64 位时间戳队列丢弃。官方指出这「在一些场合下可以用作 TCP 重传加速」。

代价是**流量放大**：`hyper` 模式对所有分组重传，实际带宽消耗会显著上升。
这是一个用带宽换延迟/可靠性的显式取舍，配置时需要有意识。

## 6. 实现与工程特征

| | OpenGNB | WireGuard |
|---|---|---|
| 语言/位置 | 用户态 C，`src/` 内所有源码 + `libs/` 内联第三方，**编译不需第三方库** | Linux 内核内（也提供多平台实现） |
| 并发模型 | **单进程多线程**：1 个 `select()` 网络 I/O 线程 + N 个 worker 线程（primary / index / secure_index / index_service / secure_index_service / detect / node / pf），线程间用**定长 ring buffer** + `pthread_kill(SIGALRM)` 唤醒 | 内核网络栈模型，per-peer 包队列 |
| 运行时状态暴露 | **共享内存控制块 `gnb.map`**（mmap），`gnb_ctl -b <map> -s` 直接 dump；`gnb_es` 也通过它双向通信 | `wg show` 通过 netlink 查询 |
| 私钥暴露面 | ⚠️ `gnb.map` 内含**明文 ed25519 私钥、`shared_secret`、`crypto_key`**。该文件权限等价于私钥权限 | 私钥在内核内存，不落盘于状态接口 |
| 配置重载 | 支持 **SIGHUP 热重启**：停旧 core、rename mmap、恢复节点与 socket，**不中断已建立的 P2P** | `wg set` 逐项修改，无需重启接口 |
| 依赖时钟 | 仅 `--crypto-key-update-interval` 开启时依赖 | **始终依赖**（时间驱动的轮换；官方列为已知局限「不可靠的单调计数器」） |
| 可审计性主张 | 无明确主张；代码量约 2.4 万行 C（`src/src` 统计） | **明确主张**「可被单个人完整审计」，刻意对比 IPsec/OpenVPN 的体量 |
| 内存占用 | 官方称可在 **32 MB 内存**的 OpenWRT 路由器上运行 | 内核实现，占用取决于对端数量（上限约 100 万 peer） |
| 平台 | Linux / Windows / macOS / FreeBSD / OpenBSD / NetBSD / OpenWRT / 树莓派 | Linux 内核 + Windows / macOS / BSD / iOS / Android |
| 已知平台限制 | **Windows 下 IPv6 不可用**；不支持 TAP 二层 | Windows 支持完整；无二层（同为三层） |

### 6.1 两者都「不做什么」

值得注意的一致性：**两者都不做流量混淆**。

- WireGuard 明确声明「不专注于混淆，混淆应该在上面一层做」，
  并说明这是为了「专注用简单实现提供扎实的密码学」；
- GNB 没有专门声明，但其协议特征同样明显（固定 UDP 端口、固定帧头结构）。

另外两者都**不支持 TAP / 二层交换**，都工作在 TUN 三层模式。

### 6.2 两者都不做 TCP 隧道

- WireGuard 明确拒绝：「TCP-over-TCP 的网络性能众所周知地糟糕」，
  建议用 `udptunnel` / `udp2raw` 在上层做转换；
- GNB 本身是 UDP，但官方提供 `gnb_udp_over_tcp` 项目
  （`src/README_CN.md:323`）作为独立的 UDP-over-TCP 中转服务。

## 7. 选型视角

### 7.1 各自的强项

**OpenGNB 的不可替代之处**（WireGuard 完全没有）：

1. **无需公网 IP 即可组网**——这是它的立身之本；
2. **NAT 穿透的穷举策略 + 网络效应**（节点越多越容易穿透）；
3. **穿透失败仍有兜底**（四种转发模型），保证「一定能通」；
4. **内网自动发现**，同 LAN 节点不必绕 WAN；
5. **去中心化**，index 只做索引、不中转数据，不构成流量瓶颈；
6. **极低资源占用**，能在 32 MB 内存的设备上跑。

**WireGuard 的不可替代之处**（GNB 完全没有）：

1. **前向保密**——密钥泄露不危及历史流量；
2. **AEAD 完整性保护**——篡改必被发现；
3. **无 nonce 重用风险**（计数器不可回绕 + 滑动窗口抗重放）；
4. **任意 CIDR** 与精确的 `AllowedIPs` 双向语义；
5. **内核级性能**；
6. **抗 DoS 的无状态 cookie 机制**；
7. **极小的可审计攻击面**，有形式化验证工作。

### 7.2 决策要点

| 如果你的问题是… | 更合适的是 |
|---|---|
| 两端都有公网可达地址，要安全传流量 | WireGuard |
| 一堆内网设备要互相访问，没有公网 IP | OpenGNB（或其穿透能力） |
| 要承载敏感数据 | WireGuard；或用 GNB 解决穿透后再在隧道内跑 WireGuard |
| 资源受限的嵌入式设备（32 MB 级） | OpenGNB |
| 需要精细的子网/ACL 控制 | WireGuard（`AllowedIPs` 双向语义 + 完整 CIDR） |
| 需要「一定能通」的兜底 | OpenGNB（四种转发模型） |
| 需要抗审查 / 混淆 | **两者都不提供**，都需要上层方案 |
| 需要后量子保密 | WireGuard 的 PSK 槽位可缓解；GNB 无对应机制 |

### 7.3 组合使用是合理的

因为两者的职责不重叠，组合是自然的：

- **用 GNB 做穿透层，用 WireGuard 做加密层**——GNB 负责把两个内网节点
  连起来（解决 WireGuard 做不到的 NAT 穿透），WireGuard 跑在这个可达性之上
  提供真正的 AEAD 与前向保密。这正是 WireGuard 官方所说的
  「在上层做混淆/加固」的思路，也是 GNB 的安全短板最直接的补法。
- **代价**是双重封装开销（GNB 28 字节 + WireGuard 32 字节 = 60 字节），
  以及需要把 MTU 相应调低（GNB 默认 1280 本身已偏保守，能容纳这个叠加）。

## 附：两个值得记住的设计智慧

**GNB 的 `node_random_sequence` 机制**：节点向 index 提交地址时生成随机数并对它签名，
index 保存「最后收到的随机数 + 签名」，在推送给查询方时一并发回；
查询方用节点公钥验签。**这样包括 attachment 在内的整个地址条目都无法被 index 伪造**——
把一个不可信的中间节点变成了「可验证但不必信任」的角色。
这是在「无中心信任」前提下很漂亮的一手。

**WireGuard 的无状态 cookie**：cookie 就是「对发送者 IP 地址的 MAC」，
密钥是服务端每两分钟轮换的秘密。服务端**不需要为每个半开连接存状态**，
因为 cookie 本身就是「服务端曾经验证过你的 IP」的可验证凭证。
攻击者无法伪造合法 IP 的 cookie，因此无法把攻击流量伪装成大量不同源 IP。
这是用密码学换掉状态表的经典做法。
