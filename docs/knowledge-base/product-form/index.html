本地 token 与 DNS rebinding

embed 之后，浏览器要能调通本机 API，两个问题必须一起解：

  • 浏览器怎么拿到 local token。 mynetd 的 token 落盘在 <MYNET_HOME>/var/run/local-api.token（0600）， 浏览器读不到；而 mynet_ui 现在完全没有 token 概念（axios 只有 baseURL: '/api'）。 建议用 Cookie：mynetd 首次 GET / 时种 HttpOnly + SameSite=Strict 的 cookie， API 同时接受 cookie 与 Bearer。HttpOnly 防 XSS 读取，浏览器自动携带，CSRF 由 SameSite 兜住。
  • 校验 Origin / Host 头。 任何网页都能让浏览器请求 http://127.0.0.1:<port>—— 只校验 token 不校验来源，恶意网页就能读本机状态甚至操作节点（DNS rebinding）。 只接受 127.0.0.1:<port> 与 localhost:<port>。这是必做加固，不是可选项。

四藏掉 api.mynet.club

「GUI 只跟本机 mynetd 说话」走到极致，结果是： 浏览器不需要知道 back 在哪，back 就能彻底退进内网。 对外只剩 gateway——一个无状态的 Go 二进制，可多实例、可挂 CDN。

gateway 两个入口（已定）

gateway
  ├── /v1/node/connect   WS    节点面 · Ed25519 身份 · presence · 推送

local-api.md §2 的措辞是对的：「relay 只做转发 + 限流 + 声明身份…… 鉴权归属与业务校验一律由 back 负责」。 control-plane.md §5.3 把「连接建立用的 Ed25519」写在「鉴权」标题下，措辞应改。

连接层的 Ed25519 是干什么的

gateway 验证 WS 连接属于哪个节点，目的是寻址与在线状态，不是授权这次请求。它支撑三件事：

  • presence：回答「节点 X 是否在线」——不验证则可被冒充
  • 定向推送：back 调 /v1/notify 推事件给某 node_id，gateway 要靠它找到那条连接
  • 按节点限流：经中继后所有节点挤在网关同一个 IP 上，只能按节点身份计数

连接身份 = 门牌号；请求授权 = back 的事。

三层三套凭证（术语分清）

层        谁 ↔ 谁                认证                    凭证
数据面    节点 ↔ 节点            gnb / wg 自己的加密      驱动密钥（gnb 非标准 ed25519 / wg X25519）
节点面    节点 ↔ gateway         X25519 DH + HMAC        复用驱动密钥（同一套）
用户面    用户/桌面 ↔ back        cookie / 登录会话       无密钥，用会话

「控制面」= 节点面 + 用户面（管理通信的总称，与数据面对称）。 cookie 属用户面；Ed25519 属节点面——两者不是一回事。

为什么节点面不用 cookie：人用会话，机器用密钥。

用户（人）节点（机器）
生命周期登录 → 有效期 → 刷新 → 登出无人值守、重启后要自动恢复
凭证形态会话 token（cookie）驱动密钥（与数据面同一套）
线上跑什么token 本身（即凭证）只有签名，私钥永不出节点
失效后果重新登录会话失效会断 WS，还要自己重新登录并存凭证

这与 ssh 私钥、sshd host key、TLS 客户端证书是同一个模型： 机器身份用密钥，用户身份用会话。 私钥的安全性不在于「磁盘上不可复制」，而在于「它从不上网络」—— 线上只出现 HMAC，截获无用；而 token 是 bearer 凭证，被看到即可冒用直到撤销。

gateway 不鉴权，只做透传 + 连接状态

WS 连接建立（像 TCP 握手）  →  只有传输状态，无密码学
   ↓
请求携带凭证 ──透传──> back 验证
   ↓
back 验证通过 → 连接置位「已鉴权 = node X」
   ↓
推送 / presence 只按这个状态路由

鉴权不鉴权靠状态解决——连接本身不鉴权， 连接的鉴权状态由 back 验证请求后置位。 这与 TCP 一致：握手只建立传输，语义由上层负责。

因此 gateway 不需要任何密钥，也不存在「公钥下发」问题—— 与「relay 不做鉴权，鉴权归 back」是同一条原则的延伸。

残余风险：连接身份是声明的

未验证的 node_id 声明意味着攻击者可以抢占推送通道、 伪造 presence。但推送内容按规范不含业务载荷 （只是「有命令待执行」），且攻击者无法真的执行命令（back 会验请求）—— 泄露的是存在性，不是数据。

节点 ↔ back 的请求鉴权：复用驱动密钥，复制数据面的 DH

gateway 不鉴权后，节点 ↔ back 的请求鉴权就成了唯一鉴权点。 不需要额外一套密钥——直接复制数据面的 DH 逻辑—— 而两种驱动最终都做 X25519 DH，只是公钥表示不同：

证据：GNB 的 ed25519_key_exchange 本质就是 X25519
libs/ed25519/key_exchange.c
/* unpack the public key and convert edwards to montgomery */
/* montgomeryX = (edwardsY + 1)*inverse(1 - edwardsY) mod p */
fe_frombytes(x1, public_key);  …edwards → montgomery…
/* montgomery ladder */
fe_tobytes(shared_secret, x2);      → 32B

WG 的驱动密钥本来就是 X25519 → 直接 DH。

机制：

节点面挑战响应（DH + HMAC）
back → node:  challenge = nonce(32B) + ts        （或请求自带 ts + 随机数）
node → back:  mac = HMAC-SHA256(shared, request)
                shared = X25519(driver_priv, back_pub)
back:         shared = X25519(back_priv, toMontgomery_if_gnb(node_pub))
                验证 mac

// gnb 节点：driver_priv = ed25519 标量（clamp 后前 32B）；back_pub 是 X25519 格式，直接 DH
// wg  节点：driver_priv = X25519 私钥
// back 只需按 algorithm 决定要不要做 edwards→montgomery —— 一个函数，不是两套逻辑
// gateway 全程只透传字节，不参与

好处：

  • 一套密钥——驱动密钥就是节点身份，不再多出「节点身份密钥」
  • 机制同源——节点面的 DH 就是数据面那套，与 GNB 的 ed25519_key_exchange 同源
  • gnb / wg 通吃——两者都最终做 X25519 DH，只差一个公钥格式转换

代价只有两条，都不致命

代价说明
back 需要一对 X25519 密钥 只需一对（不是每节点一对）。分发简单——节点本就信任 back， 可随 mynet setup 下发或内置发行版（pinning 会让轮换麻烦）
密钥不隔离 驱动密钥泄露 = 节点面一并失守。但驱动密钥本就是节点核心身份，泄露本来就是灾难级

另有一个小差别（本场景无影响）：DH + HMAC 是对称证明—— back 持有 back_priv，理论上能伪造节点的 mac。 但 back 本就是业务权威；而签名是公开可验的、DH+HMAC 只有对端能验， 对「节点向 back 证明身份」这个用途恰好够用。

relay 在 OpenWrt 上不存在

OpenWrt 不当用户连接网关的代理，所以不需要 relay 域，也不需要社区 UI。 分工随之清晰：

环境管哪些面是否需要 relay

已定：mynetd 与 Lua 的职责分界

mynetd（瘦构建）                Lua（luci.model.mynet.*）
  ├── 心跳采集与上报 ─────────────┐
  ├── 获取指令（heartbeat 的 commands[]  │
  │        或 WS 推送事件）            │
  ├── 命令分派 ───────────────────→ 执行命令
  │                                  （配置/密钥/防火墙/服务）
  ├── 收 Lua 的执行结果 ←────────── 返回结果
  └── 经 WS 上报 back              │
        （result → PATCH command result）┘

mynetd 负责通信，Lua 负责执行。 心跳、取指令、结果上报都在 mynetd；命令的实际执行在 Lua； 结果必须回到 mynetd，由 mynetd 经 WS 上报（不许 Lua 自己上报）。

这样 Lua 侧的 _handle_heartbeat_commands / _report_command_result 职责收窄为纯执行器——不再自己发心跳、不再自己回报。

注意事项：现状 heartbeat.sh 里的 _gnb_peer_heal （功能性健康检查）必须搬进 mynetd 瘦构建—— procd 的 respawn 替代不了它（进程没退出），而 cron 被 mynetd 取代后它就没有载体了。

层次关系与职责边界

mynetd（OpenWrt 瘦构建）
  └── 调 Lua 函数                    ← 单一入口
        ├── 配置 / 密钥 / 防火墙  → Lua 直接做
        └── 进程生命周期        → 委托 /etc/init.d/mynet（procd）
                                    └── respawn · SIGHUP 热重启 · hotplug

procd 是 Lua 的实现细节，不是 mynetd 要对接的一层。 mynetd 只调 Lua；Lua 里的 start_gnb / stop_gnb / restart_gnb 函数签名不变，只是实现从「exec gnb + 自己管 pidfile」换成「调 /etc/init.d/mynet」。

三类自愈需求，别混为一谈

故障 / 需求现状怎么处理procd 能替代吗
gnb 进程崩溃退出 心跳里没有这类逻辑 能respawn 秒级拉起（新增能力）
进程活着但打洞失败、peer 不可达 _gnb_peer_heal：ping peer VIP 3 次不可达 → 重启进程 （15 分钟冷却 + 启动 90s 宽限） 不能进程根本没退出，respawn 不触发。这段逻辑必须保留
从 back 取指令（reboot / 配置变更） cron 心跳每 5 分钟拉 不能与进程管理无关。要么继续轮询，要么走 WS 长连接

现状自愈的注释原文：「GNB 初次打洞失败后指数退避重试，可能长达 1 小时不自愈； restart 即可恢复」——这是功能性健康检查，与进程生命周期是两回事。

代价

  • 要改 node.conf 生成——现在写 daemon on，procd 需要 --systemd 或 daemon off（前台跑）。
  • gnb_es 子进程：现状 Lua 特意做 PPID 匹配清理。交给 procd 后主进程崩溃会重启 gnb 并重新 fork gnb_es，理论上更干净，但要验证 gnb 崩溃时 gnb_es 不会变孤儿。
  • 多节点场景需 procd multi-instance（现状单节点，够用）。
  • 要写约 30–50 行 procd 脚本，并把 rc.mynet 里的 plugin hooks / route / firewall 逻辑迁进去。

跨驱动互通：就是一条路由，放 L6

                 A 网段 → gnb_tun

双驱动节点 C 就是一台双网卡路由器：OS 路由表把包从一块网卡转到另一块。 这件事落在驱动无关的系统路由层（L6 NetworkBackend）， 驱动层各自独立、根本不需要知道对方存在。

九坑（开发前必读）

以下都是实测或源码核对过的陷阱，不是推测。

安全

坑细节
公钥编码三种假设冲突 同一列 node_keys.public_key 上： NodeHeartbeatAuthMiddleware 要求32 字节 base64（44 字符）并显式校验 strlen === 32； NodeKey.php:14 docblock 写「64 位 hex」； bundle 生成时又做 base64 → hex。 不一致会表现为「心跳鉴权失败」而非编码错误，极难定位。
→ 统一按 hex 编码（遵循 gnb 的 64/128 hex），加 algorithm 列： gnb 侧零转换，wg 的 base64 在写入边界转 hex，中间件也按 hex 解析。 注意这只解决编码；私钥布局是另一维——见下面「GNB 不是标准 ed25519」。
私钥明文存在 back，且有外发路径 NodeKey.php:24 的 private_key 在 $fillable； saveNodeKeys 明文落库并返回；generateNodeKeys 会把它组装进邮件正文。 与 control-plane.md 的「私钥永不出节点」冲突。 （查对端公钥的接口 getRouterKeys 只返回 public_key，是干净的。）
心跳用「公钥」当 HMAC 密钥 HMAC-SHA256(base64_decode(node_keys.public_key), METHOD|path|ts|body)， 容忍窗口 300s。公钥按设计可公开，所以任何读到公钥的一方都能伪造心跳。 代码 docblock 自认是已知弱点、非实现 bug，定位为过渡方案待 gateway 的 Ed25519 取代。 风险性质是「迁移窗口期暴露」。
BundleEnvelope 下发时含明文私钥 secret://node_keys/1001/private 只是 back 内部生成流程的可追溯引用， 下发时明文写入 driver intent 字段，secret:// 不下发。规范列为「迁移路径」。
DNS rebinding 任何网页都能让浏览器请求 http://127.0.0.1:<port>。 只校验 token 不校验来源，恶意网页就能读本机状态、操作节点。 embed WebUI 时必须同时校验 Origin / Host。
GNB 不是标准 ed25519——三层要分清
层是否标准说明
签名标准 RFC 8032 ed25519_sign/verify 是标准方程，stdlib Verify 互通
私钥布局非标准 落盘 clamp(SHA512(seed))，不是 seed‖public_key。 keypair.c:9-12：sha512(seed,32,private_key) 后就地 clamp （[0]&=248; [31]&=63; [31]|=64）——「再存的小动作」就在这
数据面额外操作 签名之外再做 ed25519_key_exchange：edwards→montgomery 转换 → X25519 式 DH → shared_secret
实测对比（同一 seed）： 
Go 标准 ed25519.PrivateKey (64B) = seed(32) ‖ public_key(32)
GNB 落盘的私钥 (64B)            = clamp(SHA512(seed))   ← 前 32B 不是 seed
后果：拿到 GNB 私钥无法反推 seed，也不能直接喂 stdlib 签名 （签名侧需 SignGNB 显式 clamp + 自派生 nonce）。 → 节点面复用驱动密钥时，gnb 侧要按 GNB 布局取标量 （clamp(SHA512(seed)) 前 32B）做 X25519 DH， 别拿 stdlib 的 seed‖pub 去算。 编码（hex）与布局（seed‖pub 还是 SHA512）是正交的两维。

配置与协议

坑细节
GNB 非标准掩码被静默忽略 只认 /32（且 IP 末位非 0）、/24、/16、/8、/0。 /27 /22 等 get_netmask_class() 返回 'n'， 不报错、不生效、不警告。配置错了极难发现。 192.168.1.0|255.255.255.255 也会被忽略（末位为 0）。
GNB 数据面默认加密是 XOR --crypto 取 xor(默认) / rc4 / none，手册注明「未来会支持 aes」。 XOR 是 64 字节固定周期重复密钥流，无 nonce；数据面无 MAC。 唯一的 verifycode（明文首 2 + 末 2 字节）不依赖密钥，不是完整性保护。
GNB 的 auto 模式与 WG 语义不同构 gnb 生成 route.conf 同时含 direct + forward，协议层自选 P2P 或 forward； wg 无自动 fallback，靠 L7 观测层检测并切换 peer。 不可把两者压成扁平结构。
X25519 签不了名 WG 的密钥是 DH 原语，不能用于 challenge-response 签名。 Ed25519 与 X25519 底层同曲线，但 X25519 公钥只有 Montgomery u 坐标、 丢掉了 Edwards 符号位，私钥布局也不同，不能无歧义转换。 → 节点面别走签名这条路，改走 DH（见第六节）—— 两种驱动最终都做 X25519 DH，可复用同一套驱动密钥。

实现

坑细节
IsAllowedWith 先查 deny 再查 allow 只加 AllowedPathPrefixes 而不删 deniedFragments 是无效的—— 目标路径仍被子串拦下。改白名单必须两个动作同时做。
gnb conf 目录有格式化 bug 产物 driver/gnb/conf/*/ed25519/ 下同时存在正确的 {nodeid}.public 与 %!d(string={nodeid}).pub（5 个节点各一份，65 字节）—— Go 把 %d 用在字符串上，旧产物未清理。
心跳路径与文档不符 HEARTBEAT_API_SPEC.md 写 POST /api/v1/heartbeat， 实现是 POST /api/v1/monitor/heartbeat。 另：HEARTBEAT_IMPLEMENTATION_SUMMARY 说「Ed25519 签名验证」，实现是 HMAC。
gnb_es 子进程需要显式清理 Lua 现在靠 PPID 匹配清理 gnb_es——说明 gnb 崩溃时 gnb_es 可能不自动退出。 procd 接管前必须验证这一点。
文档与代码漂移 control-plane.md 标「gateway 未实现」但代码已存在； mynet_utc VERSION=1.5.0 而 README 写 1.3.0，且其「双模式 8192/8193」 「零 malloc 热路径」与实际代码不符（热路径每包 malloc）。 读文档时以源码为准。
